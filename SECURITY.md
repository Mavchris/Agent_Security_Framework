# Security Policy

## Responsible disclosure

If you find a security issue in ASIF itself (not in the third-party threats it catalogs), please open a private [GitHub Security Advisory](https://github.com/Mavchris/Agent_Security_Framework/security/advisories) rather than a public issue. We'll acknowledge and address it as time allows — this is an academic/research project maintained outside a formal SLA.

## Current security posture

- SQL queries are parameterized throughout the codebase (`?` placeholders) — no known SQL injection vectors.
- No hardcoded secrets in the code or in git history; API keys are read from `config/.env.local` (git-ignored) via environment variables.
- No authentication or authorization on the FastAPI (`api/app.py`) or Streamlit layers — anyone who can reach the process can read/query the threat database and trigger a scan. Do not expose these outside a trusted network.
- CORS is configured via `CORSMiddleware`, restrictive by default: no origins are allowed unless the `CORS_ALLOWED_ORIGINS` environment variable is set (comma-separated list) — there is no `allow_origins=["*"]` anywhere. Review and set this explicitly before any deployment where a browser-based client on a different origin needs to call the API.
- API errors are handled by a global FastAPI exception handler: the real exception (with traceback) is logged server-side via `logging`, and the client only ever receives a generic `{"error": "Internal server error", "status": "error"}` with HTTP 500 — no internal detail (file paths, SQL structure) is exposed. `GET /health` is the one intentional exception: it still returns HTTP 200 with `{"status": "unhealthy", "error": "Internal server error"}` on failure, since a health check reporting itself degraded is a normal response for monitoring tools, not a server error.
- **Agent registry secrets**: the `registered_agents` table (`core/agent_registry.py`) never stores a secret directly. A `remote_http` agent's config can hold `auth_env_var` — the *name* of an environment variable — not the token itself; `RemoteHTTPAgentWrapper` reads the real value from `os.environ` (via `config/.env.local`, git-ignored) only at the moment of each call, never persisting it. This is enforced by convention in `core/agent_registry.py` and the registration form, not by a schema-level check — don't paste a raw token into the `config` field when registering an agent by hand (e.g. via a script or the API, if one is added later).
- **Agent registry has no access control of its own**: registering, listing, or deactivating an agent goes through the same unauthenticated dashboard/API as everything else (see the point above about no auth). Anyone who can reach ASIF can point a `remote_http` agent at an arbitrary internal URL and see the (generic, sanitized) error if it fails — this is a real, if modest, SSRF-adjacent surface, not just a data-read risk. It doesn't currently expose a way to read `config/.env.local`'s actual values (only env var *names* the operator chooses to type in), but treat agent registration as an administrative action and restrict network access accordingly, same as the rest of ASIF.
- **Monitoring logs contain real production text, stored unencrypted**: `POST /monitoring/log-request` persists the actual prompt/response text it's given (truncated to 500/1000 characters) to `monitoring_logs`/`monitoring_alerts` in `data/monitoring.db`. This can be sensitive — it's whatever a monitored production agent actually said, not synthetic test data. Mitigations currently in place: kept in a **separate database file** from `data/threats.db` (the public threat catalog), specifically so exporting/sharing "the threat catalog" doesn't also leak production monitoring history; truncation limits (not redaction). **Not in place**: no encryption at rest, no field-level masking of emails/keys/PII, no auth (same limitation as everywhere else in ASIF — anyone who reaches the API or dashboard can read this text in full). If you monitor real production traffic with ASIF, treat `data/monitoring.db` as containing sensitive data and restrict access to it (filesystem permissions, network access to the host) accordingly. Encryption at rest and redaction are not currently planned beyond the general roadmap item below — revisit if this framework moves from "confirmed on synthetic/test data" to routine use against a real production agent.

## What's not covered

Authentication, RBAC, and encryption at rest are on the roadmap (see [ROADMAP.md](ROADMAP.md)) but not implemented yet. Treat this as a local/trusted-network tool for now, not a hardened production service.
