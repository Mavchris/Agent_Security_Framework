# Security Policy

## Responsible disclosure

If you find a security issue in ASIF itself (not in the third-party threats it catalogs), please open a private [GitHub Security Advisory](https://github.com/Mavchris/Agent_Security_Framework/security/advisories) rather than a public issue. We'll acknowledge and address it as time allows — this is an academic/research project maintained outside a formal SLA.

## Current security posture

- SQL queries are parameterized throughout the codebase (`?` placeholders) — no known SQL injection vectors.
- No hardcoded secrets in the code or in git history; API keys (Anthropic, OpenAI, etc.) are read from `config/.env.local` (git-ignored) via environment variables.
- CORS is configured via `CORSMiddleware`, restrictive by default: no origins are allowed unless the `CORS_ALLOWED_ORIGINS` environment variable is set (comma-separated list) — there is no `allow_origins=["*"]` anywhere. Review and set this explicitly before any deployment where a browser-based client on a different origin needs to call the API.
- API errors are handled by a global FastAPI exception handler: the real exception (with traceback) is logged server-side via `logging`, and the client only ever receives a generic `{"error": "Internal server error", "status": "error"}` with HTTP 500 — no internal detail (file paths, SQL structure) is exposed. `GET /health` is the one intentional exception: it still returns HTTP 200 with `{"status": "unhealthy", "error": "Internal server error"}` on failure, since a health check reporting itself degraded is a normal response for monitoring tools, not a server error.

### Authentication: named API keys

The threat catalog (`GET /threats`, `/stats`, `/threat-types`, `/sources`, `/health`, and the Intelligence/Catalog dashboards) is public by design — it's third-party threat intelligence (NVD, GitHub, etc.), not something worth gating. Everything else — registering/listing/deactivating agents, running a scan, and all production monitoring data — requires a **named API key**: a label plus a high-entropy random token (`core/auth.py`), stored as `label` + a SHA-256 hash of the token in its own `data/auth.db`, deliberately separate from `data/threats.db` (public catalog) and `data/monitoring.db` (production text) so that treating either of those as freely exportable never leaks auth material. SHA-256 rather than a slow password KDF (bcrypt/argon2) is deliberate: it hashes a 256-bit random token, not a human-chosen password, so there's no dictionary/brute-force surface a slow KDF would need to defend against.

There is deliberately no unauthenticated endpoint or UI flow to create a key — that would let anyone mint their own. The only way to get one is `python scripts/maintenance/create_api_key.py <label>`, run directly on the server by an administrator; it prints the raw key once and stores only its hash. `python scripts/maintenance/deactivate_api_key.py <label>` revokes one (sets `is_active=0`, keeps the row so past attribution stays meaningful) without needing to know the key itself.

Enforcement differs by surface, because the actual access paths differ (agent registration/scanning has no HTTP endpoint at all — it's only reachable through the dashboard's direct Python imports, so an API-only check would have left it wide open):
- **API** (`api/app.py`): the 4 `/monitoring/*` endpoints (`log-request`, `stats`, `alerts`, `health`) require a valid, active key via the `X-API-Key` header, checked by a reusable `require_api_key` FastAPI dependency. Missing/invalid/inactive all return a generic `401 {"detail": "Invalid or missing API key"}` — the real reason is only in the server-side log, never echoed to the client.
- **Dashboard** (`dashboard/pages/operations.py`, the "Agent Operations" page): gated as a whole page, not per-tab or per-button, since every action on it is sensitive. The key is checked once per browser session and the resulting **label** — never the raw key — is kept in `st.session_state`, so it isn't re-verified on every click. **Known trade-off**: a key revoked mid-session stays effective in a tab that already unlocked until that browser session ends (tab close, or Streamlit session expiry) — there is no per-click re-check. If a compromised key needs to stop working immediately regardless of already-open sessions, deactivating it is necessary but not by itself sufficient; treat it the same as any credential rotation (also restrict network access to the host in the meantime).

Which key performed a sensitive action is recorded for attribution: `registered_agents.created_by_key_label`/`deactivated_by_key_label` (`data/threats.db`) and `monitoring_logs`/`monitoring_alerts.created_by_key_label` (`data/monitoring.db`) — plain `TEXT` columns, not a cross-database foreign key (SQLite can't enforce one across separate files), so a later key rename/deactivation doesn't retroactively change historical attribution.

- **Agent registry secrets**: the `registered_agents` table (`core/agent_registry.py`) never stores a secret directly. A `remote_http` agent's config can hold `auth_env_var` — the *name* of an environment variable — not the token itself; `RemoteHTTPAgentWrapper` reads the real value from `os.environ` (via `config/.env.local`, git-ignored) only at the moment of each call, never persisting it. This is enforced by convention in `core/agent_registry.py` and the registration form, not by a schema-level check — don't paste a raw token into the `config` field when registering an agent by hand.
- **Agent registry's SSRF-adjacent surface is now gated, not eliminated**: registering an agent requires a named API key (see above), but a key holder can still point a `remote_http` agent at an arbitrary internal URL and see the (generic, sanitized) error if it fails. Restrict who holds a key the same way you'd restrict any other administrative credential.
- **Monitoring logs contain real production text, stored unencrypted**: `POST /monitoring/log-request` persists the actual prompt/response text it's given (truncated to 500/1000 characters) to `monitoring_logs`/`monitoring_alerts` in `data/monitoring.db`. This can be sensitive — it's whatever a monitored production agent actually said, not synthetic test data. Mitigations currently in place: kept in a **separate database file** from `data/threats.db` (the public threat catalog); truncation limits (not redaction); reading it back (via the API or the dashboard) now requires a named API key. **Not in place**: no encryption at rest, no field-level masking of emails/keys/PII. If you monitor real production traffic with ASIF, treat `data/monitoring.db` as containing sensitive data and restrict filesystem/network access to the host regardless of the key check. Encryption at rest and redaction are not currently planned beyond the general roadmap item below.

## What's not covered

Named API keys are label-plus-secret, not full user accounts — there's no RBAC (every valid key can do everything the gated surfaces allow), no key expiry, and no rate limiting. RBAC and encryption at rest are on the roadmap (see [ROADMAP.md](ROADMAP.md)) but not implemented yet. Treat this as a local/trusted-network tool for now, not a hardened production service.
