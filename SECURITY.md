# Security Policy

## Responsible disclosure

If you find a security issue in ASIF itself (not in the third-party threats it catalogs), please open a private [GitHub Security Advisory](https://github.com/Mavchris/Agent_Security_Framework/security/advisories) rather than a public issue. We'll acknowledge and address it as time allows — this is an academic/research project maintained outside a formal SLA.

## Current security posture

- SQL queries are parameterized throughout the codebase (`?` placeholders) — no known SQL injection vectors.
- No hardcoded secrets in the code or in git history; API keys (Anthropic, OpenAI, etc.) are read from `config/.env.local` (git-ignored) via environment variables.
- CORS is configured via `CORSMiddleware`, restrictive by default: no origins are allowed unless the `CORS_ALLOWED_ORIGINS` environment variable is set (comma-separated list) — there is no `allow_origins=["*"]` anywhere. Review and set this explicitly before any deployment where a browser-based client on a different origin needs to call the API.
- API errors are handled by a global FastAPI exception handler: the real exception (with traceback) is logged server-side via `logging`, and the client only ever receives a generic `{"error": "Internal server error", "status": "error"}` with HTTP 500 — no internal detail (file paths, SQL structure) is exposed. `GET /health` is the one intentional exception: it still returns HTTP 200 with `{"status": "unhealthy", "error": "Internal server error"}` on failure, since a health check reporting itself degraded is a normal response for monitoring tools, not a server error.

### Authentication: named API keys

The `threats` table itself (`GET /threats`, `/stats`, `/threat-types`, `/sources`, `/health`, and the Intelligence/Catalog dashboards) is public by design — it's third-party threat intelligence (NVD, GitHub, etc.), not something worth gating. Everything else — registering/listing/deactivating agents, running a scan, and all production monitoring data — requires a **named API key**: a label plus a high-entropy random token (`core/auth.py`), stored as `label` + a SHA-256 hash of the token in its own `data/auth.db`, deliberately separate from `data/threats.db` and `data/monitoring.db` (production text) so that treating either of those as freely exportable never leaks auth material. SHA-256 rather than a slow password KDF (bcrypt/argon2) is deliberate: it hashes a 256-bit random token, not a human-chosen password, so there's no dictionary/brute-force surface a slow KDF would need to defend against.

There is deliberately no unauthenticated endpoint or UI flow to create a key — that would let anyone mint their own. The only way to get one is `python scripts/maintenance/create_api_key.py <label>`, run directly on the server by an administrator; it prints the raw key once and stores only its hash. Add `--expires-in-days N` to make it stop working automatically N days from now (see **Key expiration** below) — omit it for a key that never expires, the same default as before this flag existed. `python scripts/maintenance/deactivate_api_key.py <label>` revokes one (sets `is_active=0`, keeps the row so past attribution stays meaningful) without needing to know the key itself. `python scripts/maintenance/list_api_keys.py` lists every key's label, creation date, last use, and status (`active`/`inactive`/`expired`) — never the key itself, only its hash is ever stored.

Enforcement differs by surface, because the actual access paths differ (agent registration/scanning has no HTTP endpoint at all — it's only reachable through the dashboard's direct Python imports, so an API-only check would have left it wide open):
- **API** (`api/app.py`): every endpoint except the public threat catalog requires a valid, active, non-expired key via the `X-API-Key` header, checked by a reusable `require_api_key` FastAPI dependency. Missing/invalid/inactive/expired all return the same generic `401 {"detail": "Invalid or missing API key"}` — the real reason (including whether it was expiry specifically) is only in the server-side log, never echoed to the client.
- **Dashboard** (`dashboard/pages/operations.py`, the "Agent Operations" page): gated as a whole page, not per-tab or per-button, since every action on it is sensitive. The key is checked once per browser session and the resulting **label** — never the raw key — is kept in `st.session_state`, so it isn't re-verified on every click. **Known trade-off**: a key revoked mid-session stays effective in a tab that already unlocked until that browser session ends (tab close, or Streamlit session expiry) — there is no per-click re-check. If a compromised key needs to stop working immediately regardless of already-open sessions, deactivating it is necessary but not by itself sufficient; treat it the same as any credential rotation (also restrict network access to the host in the meantime).

Which key performed a sensitive action is recorded for attribution: `registered_agents.created_by_key_label`/`deactivated_by_key_label` (`data/threats.db`) and `monitoring_logs`/`monitoring_alerts.created_by_key_label` (`data/monitoring.db`) — plain `TEXT` columns, not a cross-database foreign key (SQLite can't enforce one across separate files), so a later key rename/deactivation doesn't retroactively change historical attribution.

- **`data/threats.db` is no longer just "the public catalog"**: the `threats` table on its own is safe to export/share as-is (public, third-party CTI - that's the assumption the rest of this document, and DATA_SOURCES.md, still correctly makes about it specifically). The **file**, however, also holds `registered_agents` (agent names, environments, and `config` - including a `remote_http` agent's internal `endpoint_url` and `auth_env_var` name, never the secret itself, see below) and, as of the scan-persistence work, `scan_results` (attack-payload/response snippets from real scans against real agents - see the note below). Don't assume "it's just the threat catalog" when backing up, copying, or sharing `data/threats.db` as a whole file; if you want the genuinely public part alone, export the `threats` table specifically (e.g. `GET /threats`), not the file.
- **Agent registry secrets**: the `registered_agents` table (`core/agent_registry.py`) never stores a secret directly. A `remote_http` agent's config can hold `auth_env_var` — the *name* of an environment variable — not the token itself; `RemoteHTTPAgentWrapper` reads the real value from `os.environ` (via `config/.env.local`, git-ignored) only at the moment of each call, never persisting it. This is enforced by convention in `core/agent_registry.py` and the registration form, not by a schema-level check — don't paste a raw token into the `config` field when registering an agent by hand.
- **Agent registry's SSRF-adjacent surface is now gated, not eliminated**: registering an agent requires a named API key (see above), but a key holder can still point a `remote_http` agent at an arbitrary internal URL and see the (generic, sanitized) error if it fails. Restrict who holds a key the same way you'd restrict any other administrative credential.
- **Scan results can contain real agent response text**: `scan_results.report_json` (`data/threats.db`) includes a truncated snippet of what the tested agent actually replied to each attack payload - for a `remote_http` agent backed by real business logic, that reply could echo internal details, same class of concern as monitoring logs below, just bounded to what a single scan run captures rather than continuous traffic. Reading scan results requires a named API key (same as triggering one); there's no additional redaction beyond the existing truncation.
- **Monitoring logs contain real production text, stored unencrypted**: `POST /monitoring/log-request` persists the actual prompt/response text it's given (truncated to 500/1000 characters) to `monitoring_logs`/`monitoring_alerts` in `data/monitoring.db`. This can be sensitive — it's whatever a monitored production agent actually said, not synthetic test data. Mitigations currently in place: kept in a **separate database file** from `data/threats.db`'s `threats` table; truncation limits (not redaction); reading it back (via the API or the dashboard) now requires a named API key. **Not in place**: no encryption at rest, no field-level masking of emails/keys/PII. If you monitor real production traffic with ASIF, treat `data/monitoring.db` as containing sensitive data and restrict filesystem/network access to the host regardless of the key check. Encryption at rest and redaction are not currently planned beyond the general roadmap item below.

### Rate limiting

Every endpoint gated by `require_api_key` is also rate-limited **per API key label**, not per IP — consistent with attribution already being by-label throughout (see above), and with this being a single-process, small-scale service rather than something behind a shared NAT or CDN edge. `core/rate_limit.py` implements this as a small in-memory fixed-window counter, deliberately without adding a dependency (`slowapi`/`limits`) or new infrastructure (Redis) — the same "no new infra" choice already made this session for OpenCTI, the database, and scan execution — since a by-key limiter needs a custom key function regardless of library, and the counting logic itself is small. State is process-local and does not survive a restart, the same accepted tradeoff already made for `scan_store`'s `running` rows (see [DEPLOYMENT.md](DEPLOYMENT.md)).

An invalid/unknown/expired key is rejected by `require_api_key` (401) **before** it ever reaches the limiter, so a failed attempt never counts against — or is blocked by — any real key's quota.

Default thresholds, one bucket per category (all configurable via environment variables, no code change needed):

| Category | Endpoints | Default | Env vars |
|---|---|---|---|
| `scan` | `POST /scan` | 10 / hour | `RATE_LIMIT_SCAN_MAX_REQUESTS`, `RATE_LIMIT_SCAN_WINDOW_SECONDS` |
| `read` | `GET /agents`, `GET /agents/{id}`, `GET /monitoring/stats\|alerts\|health/{agent}`, `GET /scan/results/{id}` | 120 / minute | `RATE_LIMIT_READ_MAX_REQUESTS`, `RATE_LIMIT_READ_WINDOW_SECONDS` |
| `write` | `POST /agents`, `POST /agents/{id}/deactivate` | 20 / minute | `RATE_LIMIT_WRITE_MAX_REQUESTS`, `RATE_LIMIT_WRITE_WINDOW_SECONDS` |
| `log_request` | `POST /monitoring/log-request` | **unlimited by default** (`0`) | `RATE_LIMIT_LOG_REQUEST_MAX_REQUESTS`, `RATE_LIMIT_LOG_REQUEST_WINDOW_SECONDS` |

`log_request` is exempt by default deliberately, not an oversight: this endpoint exists to receive potentially every interaction of a production agent, continuously. Capping it by default would risk silently dropping legitimate monitoring data exactly when an agent's behavior spikes — the scenario monitoring exists to catch. Set `RATE_LIMIT_LOG_REQUEST_MAX_REQUESTS` to a positive number if you want a cap anyway.

A request over the limit gets `429` with a generic-but-useful body (no internal counter/threshold state leaked) and a standard `Retry-After` header:
```json
{"detail": "Rate limit exceeded for this API key. Retry after 37 second(s)."}
```

**Deliberately not covered: per-IP rate limiting against key brute-forcing.** Limiting by key label only works once a request already carries a *valid* label — it does nothing against repeated guesses of an unknown key. This is judged an acceptable gap, not an oversight: keys are `secrets.token_urlsafe(32)` (256 bits of entropy), making brute force computationally infeasible regardless of any request-rate limit that could be placed in front of it — the entropy itself is the control here, not rate limiting. Adding IP-based limiting on top would defend against a threat (guessing a 256-bit token) that isn't realistically live.

### Key expiration

`api_keys.expires_at` (nullable) lets a key stop working automatically without needing a follow-up `deactivate_api_key.py` call. `NULL` (the default, and the value on every key created before this column existed) means no expiration — fully backward compatible, no already-issued key is affected. Set one at creation with `--expires-in-days N` (see above). `verify_key` treats an expired key exactly like a deactivated one from the client's perspective (same generic 401, see above) — only the server-side log line distinguishes `reason=inactive` from `reason=expired`. There is currently no way to change an existing key's expiration after creation (deactivate and reissue instead).

## What's not covered

Named API keys are label-plus-secret, not full user accounts — there's no RBAC (every valid key can do everything the gated surfaces allow). RBAC and encryption at rest are on the roadmap (see [ROADMAP.md](ROADMAP.md)) but not implemented yet. `POST /scan` runs in a background thread of the API process, not a real job queue — a restart mid-scan loses it silently (no resume, no staleness detection on a stuck `running` row); see [DEPLOYMENT.md](DEPLOYMENT.md#async-scans-have-no-job-persistence-across-a-restart). Treat this as a local/trusted-network tool for now, not a hardened production service.
